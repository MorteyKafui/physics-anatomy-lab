# 0038. Sign-in, sessions and class codes

- Status: proposed (waiting for Mortey's approval)
- Date: 2026-11-18
- Builds on: [0008](./0008-ai-from-the-api.md), [0011](./0011-accounts-optional.md),
  [0016](./0016-own-backend-fastapi-postgresql.md), and the master plan's "Security, privacy and
  minors" section and "Student account recovery" gap fix

## Context

Phase 3 adds accounts. Teachers sign in with an email link or Google. Students never give an
email, age or phone number: they join a class with the teacher's class code and a display name
(ADR 0011). Accounts stay optional, and the lab works signed out and offline, so nothing here sits
on the lab's critical path. The API is FastAPI on PostgreSQL with no Redis (ADR 0016), so
sessions, one-time codes and rate-limit counters all live in PostgreSQL.

## Decision

### Two kinds of principal

- **Teacher.** A row in `users`, found by email (case-insensitive) or by Google's subject id.
  Signing in for the first time creates the account; there is no separate sign-up and no
  password.
- **Student.** A row in `class_members`: a display name in one class, nothing else. A student is
  not a user and has no email. A student in two classes is two members.

### Sessions

- A session is a row in `sessions`. The browser holds a random 256-bit token (base64url) in an
  HttpOnly cookie; the database holds only its SHA-256 hash, so a database leak gives no working
  sessions.
- The cookie is `__Host-pa_session` (Secure, Path=/, SameSite=Lax) everywhere except local
  development over plain HTTP, where it is `pa_session` without Secure. The web app forwards
  `/api` to the API, so the cookie belongs to the web origin.
- **Teacher sessions** end after 7 days without use, and 30 days after sign-in at the latest.
- **Student sessions** end after 90 days without use, and 365 days (about a school year) after
  joining at the latest. Students sign in rarely and have no email to recover with, so their
  sessions are longer; a lost or cleared device is fixed with a re-join code (below).
- Use slides the idle end forward, at most once a minute per session, to keep writes low.
- Every sign-in issues a new token (rotation) and ends any session the browser already had.
  Signing out deletes the row, not just the cookie.
- A teacher may be signed in on several devices at once.

### Email sign-in links

- The link carries a random 256-bit token; the database keeps its SHA-256 hash.
- It works once and expires **15 minutes** after it is sent. Asking again does not cancel an
  earlier link.
- The link opens a web page, which posts the token to the API. A plain GET never signs anyone
  in, so mail scanners that open links cannot use them up.
- The request always answers the same way, whether or not the email has an account, so the
  endpoint cannot be used to find out who teaches here.
- Limits: 5 links per email address per hour, and 30 per network address per hour.

### Google sign-in

- Authorization code flow with PKCE (S256), a random single-use `state` and a `nonce`. The state,
  nonce and code verifier are kept in `oauth_states` for 10 minutes, and the state is also bound
  to the browser with a short-lived cookie, so a callback started in another browser fails.
- The ID token's signature is checked against Google's published keys, along with its issuer,
  audience, expiry and nonce. Only accounts whose email Google has verified are accepted.
- A Google account whose email matches an existing teacher is linked to that teacher.
- Google sign-in is off unless a client id and secret are configured. Whether teacher sign-in
  offers Google at all is still an open question in the decision log; this record makes it
  possible, not required.

### Class codes

- Six characters from a 31-character alphabet with no look-alikes (`ABCDEFGHJKMNPQRSTUVWXYZ`
  and `23456789`, so no 0, O, 1, I or L), shown as two groups of three: `7KQ-42M`. That gives
  about 887 million codes.
- Codes are generated by `secrets`, stored without the dash, and unique across all classes.
  Typing is forgiving: case, spaces and the dash are ignored.
- A code does not expire. The teacher can **rotate** it at any time (the old code stops working
  at once; students already in the class are not affected) or **close joining**.
- Wrong codes are rate-limited per network address: 20 wrong tries in 10 minutes, then a wait.
  Only wrong codes count, because a whole school class often shares one address. Each try is
  counted before the code is looked up and forgiven if it was right, so parallel guesses cannot
  all slip past the limit.
- Creating a class needs the teacher to confirm the school's permission (ADR 0011), and the time
  is recorded. AI help is off for a new class (ADR 0008).

### Display names

- 2 to 24 characters: letters, digits, spaces, `_`, `-` and `.`. Unique within a class, ignoring
  case.
- Names that look like an email address (`@`) or a phone number (seven or more digits) are
  refused, so a child cannot hand over contact details by accident.

### Re-join codes (student recovery)

- A teacher can issue a one-time personal re-join code for one student: 8 characters from the
  same alphabet, valid for **24 hours**, stored as a hash. A student has at most one unused code;
  a new one replaces the old.
- Using it signs the student in as that member and ends their other sessions (the lost device).
  Wrong re-join codes share the wrong-class-code limit.

### Protection on every change

- CORS allows only the configured web origin, with credentials.
- Every POST, PUT, PATCH and DELETE that carries an `Origin` header must come from an allowed
  origin, and a request carrying the session cookie must carry `Origin`. With SameSite=Lax this
  stops cross-site request forgery without a second token.
- Rate-limit counters are rows in `rate_limits`, counted in fixed windows. An IPv6 address counts
  by its /64. Starting a Google sign-in is limited to 30 per address in 10 minutes.
- The client's address comes from the header the proxy in front sets (`cf-connecting-ip` behind
  Cloudflare). Preview, staging and production refuse to start without `CLIENT_IP_HEADER`, or
  every visitor would share the proxy's address and one limit. The API must be reachable only
  through that proxy, or the header could be forged.
- Every sign-in, sign-out, join, rotation and refusal is logged as a structured event with the
  principal's id, never the email or display name.

### Email delivery

Email goes through one small interface. Locally and in tests it is written to the log and kept in
memory; in preview, staging and production the API refuses to send sign-in links until a provider
is configured. Choosing the provider (Cloudflare Email Service or Resend) is still Mortey's call.
Sending happens in the request for now and moves to the job queue when Procrastinate arrives.

## Consequences

- No passwords are ever stored, and no student contact details exist to leak.
- A student who clears their browser needs their teacher for a re-join code. That is the price of
  holding no student email.
- Sessions can be revoked at once, because every request checks the database.
- One extra query per request for the session. That is fine at the planned scale; a cache can be
  added if load tests (Phase 3) say otherwise.
- Two small leaks are accepted. Someone holding a class code learns whether a display name is
  already in that class (the "name taken" answer). And an email link is not tied to the browser
  that asked for it, so a teacher tricked into opening someone else's link is signed in as that
  person. Neither exposes a student's work.
- The rules above (lifetimes, expiry, code length) are constants in `apps/api/app/auth/policy.py`,
  so a change to them is one reviewed edit plus a new record.

## Alternatives considered

- **JWTs instead of server-side sessions.** Rejected: they cannot be revoked before expiry, and
  the plan already keeps state in PostgreSQL.
- **Signed (itsdangerous) email links.** The plan mentioned itsdangerous. A random token with a
  stored hash is simpler, works only once, and needs no signing secret to manage.
- **Authlib for Google.** The plan named it. The code exchange is one POST, and Authlib has no
  type hints, which strict pyright refuses; the flow is written with httpx, and the ID token is
  checked with joserfc (by Authlib's author).
- **A student password or PIN.** Rejected: children forget them, and teachers already handle
  recovery with re-join codes.
- **Expiring class codes.** Rejected for now: teachers print codes on worksheets. Rotation and
  closing joining cover a leaked code.
